## Problem Statement

Across asoe2 (FastAPI/LangGraph backend) and asoe-ui (Next.js/React frontend), there are roughly 150 test files spanning unit, integration, sandbox, e2e, Playwright, accessibility, architectural, and component test layers — likely 1000+ assertions in total. Despite this volume, basic functionality breaks and ships undetected. The user reports test escape at every layer (UI/backend contract drift, recipe correctness, sandbox-vs-real divergence, UX rendering), with the team's process discipline intact (regression tests get written, flakies are not muted, skipped tests are not common).

When all layers leak simultaneously, the cause is not in any single layer. It is in the testing philosophy that runs through all of them.

## What Makes This Cool

You already have a rare strength most teams don't: **machine-readable specifications** sitting in the repo as first-class artifacts. The audit-bearing field registry (`compliance/audit_bearing_registry.yaml`, 107 fields, 11 AnalysisData classes) is a real specification. `constraints/specs.py` is a real specification (every allowed intent, recipe, resolution action, override reason tag is a Pydantic Literal). `openapi/asoe2.openapi.json` is the HTTP contract. The ADRs (`docs/adr/`) are architectural specifications. These exist because someone took the time to write them. The leverage opportunity: turn each one from documentation into a test oracle, so that any drift between code and spec fails CI.

The result: the same team that ships 1000+ tests today gets 1000+ self-extending tests, where adding a new intent or recipe automatically expands contract coverage with zero manual test writing. Every spec becomes a test generator. The cross-repo seam (asoe2 ↔ asoe-ui) gets bidirectional gates so neither side can drift without the other knowing.

## Constraints

- **Two-repo system.** asoe2 (Python/FastAPI/LangGraph/Pydantic) and asoe-ui (Next.js/React/TypeScript). Contract tests must run cross-repo or the seam keeps leaking.
- **In-flight architecture.** The Verdict 2026-04-22 workshop landed recently — `audit_bearing_registry.yaml`, `EvidenceBlock`, `AUDIT_CONTEXT_MISSING` terminal status are all current. The strategy must build on this, not refactor it.
- **Existing CI is GitHub Actions** in both repos. No new platforms. Reuse existing runners, secrets, artifact storage.
- **Small team, AI-assisted dev.** Strategy should compress nicely under Claude Code: spec → generated tests is exactly the kind of mechanical work where AI compounds.
- **No real production integrations available in this sandbox.** Recorded-tape integration testing (Approach C) is deferred to a later phase.

## Premises

**P1. Root cause is uniform across layers.** All three observed leak types (coverage gap, specification gap, mock/fixture lies) collapse to one: tests assert *implementation against implementation*, not *implementation against specification*. When a recipe drifts from the registry, no test fails. When `MOCK_HEALTH` drifts from real `/health`, no test fails. When the UI's `TerminalStatus` union drifts from `contracts/models.py::TerminalStatus`, the type system can't catch it because the union is hand-written, not generated.

**P2. The specs are already there; the leverage is the glue.** `audit_bearing_registry.yaml`, `constraints/specs.py`, `openapi/asoe2.openapi.json`, ADR documents — these are existing assets that are not yet used as test oracles. The team has done the hard part. The strategy turns them into oracles.

**P3. The cross-repo seam needs bidirectional gates.** asoe2 must publish the OpenAPI as a CI artifact; asoe-ui must consume it and regenerate its types in CI. Neither side can drift without the other side's CI catching it.

**P4. 100 spec-derived tests beat 1000 example-based tests.** A small layer of spec-anchored contract tests on top of the existing pyramid will catch the cross-cutting bugs that no per-layer test can. The fix is not "write more tests." It is "promote a small, generative layer that all other tests anchor to."

## Approaches Considered

### Approach A: Spec-Oracle MVP (~2 weeks human / ~3 days CC)

Pick five spec sources (`audit_bearing_registry.yaml`, `AllowedIntent`, `AllowedRecipeName`, OpenAPI, `AllowedResolutionAction`). Write one contract test per source that fails when the impl/mock diverges. Add a CI gate that regenerates `openapi/asoe2.openapi.json` and fails PRs that diff it. Add a `tests/contract/` directory in both repos.

Pros: ships in two weeks, catches the literal drift surfaced in the audit (TerminalStatus, OpenAPI staleness, MOCK_STATS drift). Establishes the pattern: spec is the test oracle.

Cons: doesn't touch recipe correctness or mock-vs-real divergence. Two of the three leak types stay open. Will need a second strategy in two months.

### Approach B: Spec-Derived Test Generation (~6 weeks human / ~2 weeks CC) — RECOMMENDED

All of A, plus generate tests *from* the registries:

- For each `*AnalysisData` class in `contracts/models.py`, auto-generate a registry-coverage test that reads `audit_bearing_registry.yaml` and asserts every field marked audit-bearing or conditional has a populating recipe path.
- Generate `StubGateway` responses from the same Pydantic models gateways return. A stub that fails its own model's schema validation cannot ship — the stub IS a contract.
- Use `polyfactory` (or Hypothesis) to fuzz Pydantic models for property tests on recipe inputs.
- Cross-repo: asoe2's CI publishes `openapi/asoe2.openapi.json` as a GitHub Actions artifact. asoe-ui's CI downloads it, runs `openapi-typescript`, and fails if the regenerated `src/types/generated.ts` differs from committed.
- Hand-written enum unions in `src/types/exceptions.ts` get retired in favor of imports from `generated.ts`. The `TerminalStatus` drift surfaced in the audit becomes structurally impossible.

Pros: self-extending — adding a new intent/recipe automatically gains contract coverage in both repos, no manual test writing required. Schema-validated mocks close the sandbox-lies category for the synthetic-shape failure mode. Closes the cross-repo seam where half the audit-found drift lived.

Cons: requires a cultural shift toward spec-first thinking. Pydantic ↔ TypeScript bridge has known edge cases (datetime serialization, discriminated unions). Doesn't catch recipe-correctness bugs that aren't expressible as schema invariants.

### Approach C: Full Property + Recorded-Tape (~3 months human / ~6 weeks CC)

All of B, plus:

- Hypothesis property tests for *invariants* — for any valid input matching the registry's audit-bearing tier, the recipe's output must populate every required field. For any conditional field with a `depends_on` predicate, the predicate must evaluate consistently with `_predicate_holds`. For any final state of the LangGraph pipeline, the lifecycle invariants must hold.
- VCR-style recording of real OMS/SAP/SLA gateway interactions during a sanctioned sandbox session, replayed in CI. Closes the sandbox-vs-real divergence category for behavioral mismatch (not just schema).
- Mutation testing (`mutmut` for Python, Stryker for TypeScript) against critical paths. Surfaces tests that pass even when the code under them is broken — the highest-leverage test-quality measure.

Pros: catches recipe-correctness bugs, sandbox-vs-real divergence, AND identifies tautological tests. Multi-year compounding payoff.

Cons: three months is a quarter; bugs keep shipping while infra is built. Better as a follow-on to B than a starting point. Recorded-tape requires sanctioned access to real SAP/OMS/SLA endpoints, which is operationally heavy.

## Recommended Approach

**Approach B — Spec-Derived Test Generation.** It directly addresses the root cause (P1: tests-vs-impl instead of tests-vs-spec), is sized to land in one quarter, addresses all three leak types named (coverage / spec / mock), closes the cross-repo seam, and naturally upgrades to C as a follow-on rather than a rewrite.

### Implementation Plan (B)

Three concurrent lanes over six weeks. Quick wins shipped weekly.

#### Lane 1 — asoe2 spec-as-oracle (Weeks 1–4)

**Week 1: OpenAPI gate + intent/recipe parity**

- Add `scripts/regenerate-openapi.py` that boots FastAPI in test mode, calls `app.openapi()`, writes to `openapi/asoe2.openapi.json` with stable key ordering.
- New GitHub Action `openapi-drift.yml`: runs `regenerate-openapi.py` on every PR, fails on `git diff --exit-code openapi/asoe2.openapi.json`.
- New `tests/contract/test_intent_recipe_parity.py`: asserts every value in `AllowedIntent.__args__` has a corresponding recipe in `AllowedRecipeName.__args__` and a skill file in `skills/`. Fails the moment a new intent ships without a recipe.

Quick win: this catches every drift class my prior architecture audit surfaced. AUDIT_CONTEXT_MISSING UI gap, OpenAPI staleness, MOCK_STATS drift — all caught structurally, not by re-running an audit.

**Week 2: Audit-bearing registry coverage**

- New `tests/contract/test_audit_registry_coverage.py`: parses `compliance/audit_bearing_registry.yaml`. For each `*AnalysisData` class in `contracts/models.py`, asserts every audit-bearing field is populated by at least one recipe path in `recipes/`. For each conditional field, asserts the `depends_on` predicate is parseable by `_predicate_holds` (reuse `api/analysis_composer.py::_predicate_holds`).
- Test must enumerate gaps and fail with a structured report ("`PriceHoldAnalysisData.foo` is registry-required but no recipe populates it"). Initial run will surface the silent gaps that exist today.

Quick win: each silent gap becomes a fixable PR.

**Week 3: Schema-validated stubs**

- Refactor `tests/conftest.py` and `api/sandbox_gateways.py`: every `StubGateway` response's `.data` field gets validated against the matching Pydantic model gateways return. A stub that fails its own model's `model_validate` raises at import time, not at test runtime.
- Add `tests/contract/test_stub_schema_conformance.py`: enumerates every stub registered by `register_sandbox_gateways()` and asserts the response data matches the corresponding Pydantic model.
- Type the stub registration: `register_gateway(StubGateway[OmsInventoryResponse]("oms", responses=...))` — generic-typed so static type checking catches stub-vs-model drift.

Quick win: 3+ stale stubs surfaced. Sandbox vs real schema-shape divergence becomes structurally impossible.

**Week 4: Property-based fuzzing**

- Add `polyfactory` (or `hypothesis-pydantic`) as a dev dependency.
- New `tests/contract/test_recipe_invariants.py`: for each recipe class in `recipes/`, generate 100 valid inputs via Polyfactory's `ModelFactory`, run the recipe, assert the output validates against the recipe's declared output type. This catches recipe-correctness bugs at the type-shape level.
- New `tests/contract/test_validate_types_invariants.py`: feed `validate_types` 1000 generated `ExceptionRecord` instances; assert no node raises and `final_status` is in `LIFECYCLE_STATES`.

Quick win: 1+ recipe edge case the prior 1000 example-based tests missed.

#### Lane 2 — asoe-ui contract gates (Weeks 4–6, concurrent with Lane 1 finish)

**Week 4: OpenAPI consumption pipeline**

- asoe2's CI now publishes `openapi/asoe2.openapi.json` as a workflow artifact on every push to `main`.
- asoe-ui's CI gains a job that downloads the artifact (via `gh run download` or repository_dispatch event), runs `openapi-typescript` against it, diffs the regenerated `src/types/generated.ts` against the committed copy, fails on diff. The existing `tests/architectural/openapi_drift.test.ts` is the local-dev version of this gate; the CI version pulls from the source repo.
- For local dev, a new `bun run regen:types` script handles the same flow against a sibling checkout of asoe2.

**Week 5: Hand-written union retirement**

- Audit every hand-written union in `src/types/exceptions.ts` (`Intent`, `LifecycleState`, `TerminalStatus`, `ResolutionAction`, etc.).
- Replace each with `import type { components } from "./generated"; type Intent = components["schemas"]["AllowedIntent"];` (or whatever `openapi-typescript` produces).
- The `TerminalStatus` drift surfaced in the audit (UI missing `AUDIT_CONTEXT_MISSING`) becomes structurally impossible because the type comes from the OpenAPI now.
- New `tests/contract/test_enum_parity.test.ts`: for each enum, assert the union of values matches what `MOCK_HEALTH` returns. Closes the MOCK_HEALTH drift class.

Quick win: zero hand-written unions remain. Drift becomes a type error, not a runtime bug.

**Week 6: Section render coverage**

- For each `*AnalysisData` interface in `generated.ts`, write a render-coverage assertion in `tests/contract/test_section_render_coverage.test.tsx`: every audit-bearing field has a matching `EvidenceBlock` render path in the section component, and every conditional field has a matching `useConditionalField` call.
- Detection of new fields: when asoe2 ships a new audit-bearing field and the OpenAPI updates, this test fails until the UI section renders it.

Quick win: render gaps become a CI failure, not a user complaint.

#### Lane 3 — Cross-cutting tooling (concurrent, ~1 week distributed)

- "Spec coverage" metric: a small script (`scripts/spec-coverage.py`) that walks `audit_bearing_registry.yaml`, `constraints/specs.py`, OpenAPI, and ADRs, then walks the test suite to compute "% of spec elements verified by at least one contract test." Reports to `~/.gstack/analytics/` and surfaces in PR descriptions.
- Pre-commit hook: regenerates OpenAPI and `generated.ts` automatically. Manual edits to `generated.ts` rejected with a hint to run `bun run regen:types`.
- Documentation: `tests/contract/README.md` in each repo. Names the four spec sources, explains the pattern, gives templates for adding new contract tests.

## Open Questions

1. **Polyfactory vs Hypothesis-Pydantic** — Polyfactory has cleaner Pydantic V2 support; Hypothesis has a richer shrinking story. For Lane 1 Week 4, pick one. Recommendation: Polyfactory for fixture generation, Hypothesis for invariant tests. Decide in PR.
2. **OpenAPI artifact distribution** — GitHub workflow artifact (simple, default-retention 90 days) vs publishing to a versioned npm package (`@asoe/openapi`) consumed by asoe-ui. Workflow artifact is right for V1; npm package is right when there are 3+ consumers.
3. **What to do with the existing `tests/sandbox/`?** — Once schema-validated stubs land, parts of `tests/sandbox/db|llm|ui` may become redundant. Plan a one-day cleanup pass at the end of Week 3 to retire tests that the new contract layer makes obsolete.
4. **ADR enforcement** — ADRs (`docs/adr/`) are prose. Out of scope for V1 (hard to mechanize). Future phase: extract structured invariants from ADR markdown headers (e.g., "ADR-025: gateway reads before shadow") and codify as an `architecture/test_adr_invariants.py` checks.

## Success Criteria

**Quantitative:**
- Contract tests catch 100% of cross-repo drift before merge. Verifiable by: open a test PR that introduces drift on purpose, watch CI fail.
- Zero manual-edit `StubGateway` responses by end of Week 3; all derived from Pydantic models or schema-validated.
- Zero hand-written enum unions in `src/types/exceptions.ts` by end of Week 5.
- Spec coverage metric climbs from baseline (~30%, estimated) to >80% by end of Week 6.
- Property-based fuzzing surfaces ≥1 real bug missed by all prior example-based tests by end of Week 4.

**Qualitative:**
- When a new intent is added to `AllowedIntent`, contract tests in BOTH repos start failing until: (a) a recipe ships, (b) a skill ships, (c) the UI label/section ships. The "what's missing" question is answered by red CI, not by review.
- New contributors writing tests reach for `tests/contract/` patterns first when adding a feature; the spec-as-oracle pattern is documented and discoverable.

**Leading indicators (visible weekly):**

- W2: 5+ silent registry-coverage gaps surfaced and fixed.
- W3: 3+ stale `StubGateway` responses caught.

- W5: Hand-written unions retired.

## Risks

**R1. Generated tests over-fit to spec, miss real bugs.** Spec-derived tests catch what's *written* in the spec; bugs outside the spec's vocabulary are still missed. Mitigation: spec tests are an additive layer. Keep all existing example-based tests. The pyramid grows a new top, doesn't replace the base.

**R2. Pydantic ↔ TypeScript bridge edge cases.** datetime serialization, discriminated unions, generic types. Mitigation: pin `openapi-typescript` to a known-good version; document edge cases in `tests/contract/README.md`; treat the generated file as the authoritative shape and adjust Pydantic models if necessary, not the other way around.

**R3. Cultural pushback on spec-first.** Devs may bypass by editing generated files directly or hand-writing types alongside generated ones. Mitigation: pre-commit hook makes regeneration idempotent; CI rejects manual edits to generated files; documentation makes the pattern obvious; first PR that catches a real bug becomes the case study.

**R4. CI artifact size / retention.** OpenAPI JSON is small (~50KB), so this is unlikely to bite. But if other artifacts grow, retention policy matters.
