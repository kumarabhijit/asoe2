## Key Interactions to Verify
- New intent added to `AllowedIntent` → contract tests in BOTH repos fail until recipe + UI label/section ship
- New audit-bearing field added to `audit_bearing_registry.yaml` → recipe must populate it OR `final_status` routes to `AUDIT_CONTEXT_MISSING`
- New `*AnalysisData` class added → registry-coverage test enumerates required fields and verifies at least one recipe path populates each
- `AUDIT_CONTEXT_MISSING` terminal status → UI renders an explicit placeholder section (not generic fallback)
- `EXECUTING` lifecycle state never appears in any fixture, mock, or response

## Edge Cases
- Recipe receives a valid input where a conditional field's `depends_on` predicate fails → field is structurally omitted, not rendered as dash/N/A
- Pydantic model schema drift in `StubGateway` response → import-time validation error, not silent test pass
- OpenAPI regeneration produces a diff that wasn't committed → CI gate fails the PR
- `generated.ts` regeneration produces a diff that wasn't committed → CI gate fails the PR
- `MOCK_HEALTH.allowed_intents` contains a value not in `AllowedIntent.__args__` → enum-parity test fails

## Critical Paths
- `ingest → classify → load_skill → validate_circuit_breaker → select_recipe → resolve_dependencies → validate_types → shadow_audit → execute_recipe → apply_effects → build_analysis` for every (intent, recipe) pair in `INTENT_REASON_TAGS`
- Property-based: for any valid `OrderEvent` matching a registered intent, the full pipeline produces a `final_status` in `LIFECYCLE_STATES` and an analysis that satisfies the registry
- Cross-repo: asoe2 main → OpenAPI artifact → asoe-ui PR consumes → regenerate types → diff-gate

### W7 — Playwright flow registry
- `e2e/flows/*.yaml` + `e2e/flow-runner.spec.ts` (asoe-ui) — YAML-declared flows; runner derives one Playwright test per flow.
- Initial flows (one per file):
  - `email-order-entry-from-inbox.yaml` — entry `/inbox`, click email-order-entry item, expect back-to-customer-inbox affordance, click it, expect `/inbox/customer`. Catches V1.
  - `inbox-item-click-behavior-catalog.yaml` — for each declared inbox-item type, declares whether click jumps to detail page or populates right pane. Catches V3 (silence is not a default — every type must be declared).
  - `case-to-exception-detail-roundtrip.yaml` — case detail → exception detail → back; assert sign-out persists at every step. Catches V2 from a flow angle, complementing the W6 invariant.
  - `signin-to-home.yaml`, `signout-from-each-role.yaml`, `exception-triage-approval.yaml` — golden paths.

### Behavioral edge cases
- Forward/back browser navigation across case ↔ exception detail must preserve the route's authenticated chrome (sign-out, user-menu).
- Inbox item click behavior must be declared per-item-type; an undeclared type is a test failure, not silent passthrough.
- Context-aware back-targets: navigating to a shared destination (exception page) from different entry paths (customer inbox vs. exception queue) must offer entry-path-appropriate back affordances, not only the most recent queue.
